# Complete task ownership

A complete task retains ownership across model Jobs, waiting, deployment and repair. Job exit alone does not release its slot. `MAX_ACTIVE_WORKFLOWS=-1` is the shared code and template default: it removes only the count of complete workflows. Set an integer from 1 through 10000 to serialize or bound complete tasks; zero, other negatives, fractions and invalid text reject startup. Restart/recreate the application after changing this private environment setting. Never edit the derived `workflow_settings.capacity` database row as another policy source.

Single-conversation serialization, global/per-user Job limits, executor availability, memory and disk protections remain independent. A capacity of 1 keeps an active workflow's slot during waits and failed attempts until verified completion; changing the capacity does not cancel already running work.

`pp_agent_workflow` is the compatible agent tool name. Start with `status`, then update `phase` or `block`. `complete` requires the current revision, actual functional/cleanup evidence and no remaining background work. It requests closure; the server releases ownership only after its linked execution exits and there are no pending inputs or scheduled continuations. A wait/repair reuses its workflow identity. Epoch-bound authority rejects stale or forged updates. Remote transport disconnects retain uncertain execution ownership until reconciled rather than silently starting duplicate work.

Users, projects, conversations, files, preferences and workflow ownership stay in the deployment's database/state. Additive migrations `2026110802` and `2026110803` create the workflow tables and bindings. Existing conversations are not silently reclassified as complete tasks; an authorized administrator may create an operator task with `node dist-server/server/workflow-cli.js enqueue --database /path/to/app.sqlite --key unique-key --title task-title --user USER_ID`. Bind only an empty acceptance conversation after verifying active ownership. The `bootstrap` compatibility command is only for a database without an installed workflow ledger; normal upgraded databases must not use it. Stop dispatch and back up state before an operator migration. Restoring a prior database would lose subsequent work and is separate from code rollback.

The public password login and tenant isolation are unchanged. Optional trusted host and Remote Worker transports use the same ownership protocol only when configured; the default installation does not enable a host root bridge.
